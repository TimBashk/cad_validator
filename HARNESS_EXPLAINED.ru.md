# Как устроен грейдер Sling Lift — подробное объяснение

Это личный разбор, не для сдачи. Записка для проверяющих лежит в
`test_example3/FreeCAD/4_sling_lift/NOTES.md`.

## Общая схема

Работа разделена на два файла, и это разделение — главная архитектурная идея:

```
harness.py (обычный Python, без FreeCAD)
   │
   │ 1. запускает:  freecadcmd measure_stage.py  candidate.FCStd
   │                      │
   │                      ▼
   │               measure_stage.py (внутри FreeCAD)
   │               открывает документ, меряет, «шевелит»
   │               пишет measure.json + delivered.stl
   │                      │
   │ 2. читает   ◄────────┘
   │ 3. берёт эталон из baseline.json (тот же замер, но эталона)
   │ 4. сравнивает кандидата с эталоном → 6 оценок от 0 до 1
   ▼
JSON {score, max_score, subscores}
```

- **`measure_stage.py` только собирает факты**: «тут 57 тел», «шарнир
  разошёлся на 6 мм», «этот размер меняет форму».
- **`harness.py` только судит**: «57 из 57 тел совпали → 1.0».

Зачем так:
- оценку можно отлаживать без FreeCAD: ключ `--score-from` принимает готовый
  замер, и проверка идёт секунды, а не 3 минуты;
- макросы кандидата исполняются в отдельном процессе FreeCAD, а не в
  процессе грейдера;
- кандидат и эталон меряются **одним и тем же кодом**, поэтому сравнение
  честное.

# Часть 1. `measure_stage.py` — что и как измеряется

Скрипт работает внутри `freecadcmd`. Ему доступны только стандартная
библиотека Python и API FreeCAD, `numpy` там нет. Метод `measure()` по
очереди собирает 8 разделов.

## 1.1. `open()` — открыть кандидата

`task.toml` принимает три формата: `.FCStd`, `.py` и `.FCMacro`.
- `.FCStd` просто открывается.
- Скрипт исполняется, и измеряется документ, который он оставил активным.

## 1.2. `build` — собирается ли документ

```python
doc.recompute()
invalid = объекты, у которых в State есть "Invalid" или "Error"
```

Это сырьё для «ворот» (gate): если геометрии нет совсем, остальное оценивать
бессмысленно.

## 1.3. `delivered` — что именно сдано

**Проблема.** В примерах в документе лежат исходные подсборки (группа
`Sub_Assemblies`), и они же подключены в главную сборку через
`AssemblyLink`. Если собрать «все тела в файле», лифт посчитается дважды.

**Решение** (`root_assemblies`): сданное изделие — это сборки, которые никто
не включает в себя:

```python
for a in doc.Objects:
    if a — Assembly и среди a.InList нет ни Assembly, ни AssemblyLink:
        это корень
```

Если сборок нет вовсе, сданным считается всё видимое на верхнем уровне. Это
нужно для кандидата, который смоделировал лифт без Assembly.

**Детали сборки** (`parts_of`) обходятся рекурсивно, с запоминанием **пути
от корня**, например `"_1_Pantograph.Washer_A001."`. Путь пришлось вводить
из-за бага, найденного при разведке:
- у `App::Link` нет `getGlobalPlacement()`;
- деталь внутри гибкой `AssemblyLink` не знает своё мировое положение, его
  знает только корень.

Поэтому форма и положение берутся через корень:

```python
Part.getShape(root, "путь.", transform=True)                 # форма в мировых координатах
App.GeoFeature.getGlobalPlacementOf(obj, root, "путь.")      # поза
```

Я проверил: сумма тел совпала с формой корня до кубического миллиметра
(57 тел, 966 577 мм³).

**По каждому телу** (`solid_record`) записывается:

| Величина | Зачем |
|---|---|
| объём, площадь | размер и «полнота» детали |
| центр масс, тензор инерции | для общей инерции |
| **главные моменты инерции** (отсортированы) | «отпечаток» формы, не зависящий от поворота |
| **габариты в собственных осях** | тело поворачивается в свои главные оси инерции, и только потом берутся размеры |

Все эти величины не меняются ни при повороте, ни при **отражении**. Поэтому
сравнение деталей не зависит от того, как кандидат ориентировал модель и не
зеркальная ли она. Зеркальность проверяется отдельно, по сетке.

Ещё стадия экспортирует **`delivered.stl`** — сетку всего изделия для
сравнения формы в harness.

## 1.4. `joints` — шарниры

Шарниры собираются рекурсивно из `JointGroup` и из `AssemblyLink`, с
удалением дублей: один и тот же шарнир виден и через группу, и напрямую. По
каждому записывается:

```python
{
  "type": "Revolute",
  "parts": ["Bar_10x30x151", "Washer_A"],   # какие ДЕТАЛИ соединяет
  "same_part": False,                       # не соединяет ли деталь саму с собой
  "frames": [ {origin, axis}, {origin, axis} ],  # СК каждой стороны в мире
  "residual": {"gap": 0.0, "tilt": 0.0},    # насколько разошлись стороны
  "value": 41.41,                           # текущий угол / ход
  "limits": {"LengthMin": -180, ...}
}
```

**Детали, а не грани.** Шарнир ссылается на грань или ребро
(`Body.Fillet.Edge31`). Через `UtilsAssembly.getMovingPart` ссылка
превращается в подвижную деталь. Это нужно, чтобы увидеть фиктивный шарнир
между двумя гранями одного тела.

**Невязка** (`residual`) — главный признак «сомкнутости». Для каждой стороны
берётся система координат шарнира (JCS) в мире; `Placement1/2` в
FreeCAD 1.1 уже включают смещения `Offset`:

| Тип | `gap` (мм) | `tilt` (°) |
|---|---|---|
| Fixed | расстояние между началами | угол поворота между СК (переворот на 180° допустим) |
| Revolute | расстояние между началами | угол между осями Z |
| Slider, Cylindrical | расстояние от начала 2 до **линии** оси 1 (вдоль оси ездить можно) | угол между осями |
| Ball | расстояние между началами | — |

**Обе системы координат** записываются для подсчёта шага между осями на
звене (раздел 2.2). У несомкнутого шарнира каждая сторона всё равно
показывает, где находится отверстие своей детали.

## 1.5. `solve` — решается ли сборка «как есть»

Вызываю `asm.solve()` без каких-либо изменений и смотрю код возврата,
насколько сдвинулись детали и худшую невязку. Затем восстанавливаю исходные
позы. Согласованная сборка решается на месте. Противоречивые фиктивные
шарниры ломают решатель: у `dummy_joints` получилось `rc = -1`, разрыв 6 мм
и перекос 62°.

## 1.6. `articulation` — двигается ли механизм

Это самая трудная часть. Сначала я опробовал штатные способы, и ни один не
подошёл:
- **пределы** (`min = max = цель`): `solve()` их игнорирует;
- **симуляция** (Simulation + Motion): без графического интерфейса не
  генерируется;
- **вспомогательные шарниры** `Distance` и `Angle`: у слайдера опоры —
  линии, и `Distance` между соосными линиями всегда 0; `Angle` в FreeCAD —
  угол между осями, а не поворот вокруг оси.

Сработала **эмуляция перетаскивания мышью**, функция `drag()`:

```
1. взять подвижный шарнир (Slider → сдвиг 5 мм, Revolute → поворот 3°)
2. взять деталь на одной его стороне
3. сдвинуть или повернуть её ВДОЛЬ СОБСТВЕННОЙ ОСИ шарнира
4. временно закрепить её (добавить GroundedJoint)
5. asm.solve() — решатель обязан подтянуть остальную цепь
6. записать: rc, сколько деталей сдвинулось, худшую невязку
7. удалить временное закрепление, восстановить ВСЕ позы
```

Как читать результат:
- механизм работает: `rc = 0`, все шарниры сомкнуты, сдвинулось много
  деталей (эталон: 41 из 43);
- механизм жёсткий: решатель не находит решения;
- механизм «разлетается»: `rc = 0`, но шарниры разошлись. Поэтому невязка
  записывается рядом со счётчиком сдвинутых деталей.

**Деталь со сдвигом.** `mp.Placement` задан в системе координат родителя, а
сдвиг вычислен в мировых координатах. Поэтому сдвиг пересчитывается через
родительское преобразование:

```python
parent = global_placement(mp) * mp.Placement.inverse()
mp.Placement = parent.inverse() * move * parent * mp.Placement
```

**Оптимизации времени:**
- первыми перетаскиваются слайдеры, потому что в лифте именно слайдер —
  главная степень свободы;
- для каждого шарнира есть 4 варианта (две стороны × два направления), но
  после первого чистого успеха остальные не пробуются;
- есть бюджет времени (класс `Budget`), по умолчанию 40 % от 240 с.

## 1.7. `parametric` — где живут размеры

Собирается вся параметрика документа:
- размерные ограничения в эскизах: `Distance`, `Radius`, `Angle` и т. п., с
  флагом «ведущее» (driving) и с формулой, если она есть;
- ячейки таблиц (Spreadsheet);
- свойства VarSet;
- все формулы `ExpressionEngine`;
- список тел, попавших в сданное изделие (`delivered_bodies`).

И отдельно **доля параметрического объёма**, функция `content_volumes`.
Ссылка детали проходится насквозь до содержимого:
`App::Link → App::Part → PartDesign::Body / Part::Feature`. Объём
суммируется по типу:
- `PartDesign::Body` — параметрическая деталь;
- голый `Part::Feature` — «мёртвое» тело: импорт или результат «посчитал и
  забыл».

Эталон: 94 % объёма — параметрические тела, 6 % — импортированный крепёж.

## 1.8. `drive_probe` — влияет ли размер на форму

Ключевой вопрос задания — «размеры управляют геометрией, а не просто
существуют». Проверяется он напрямую:

```
для каждого размера:
    отпечаток_до = (объём, площадь, габаритная коробка С ПОЛОЖЕНИЕМ) тела-владельца
    изменить размер на +5 %   (угол на +2°)
    пересчитать ТОЛЬКО это тело и его входы
    отпечаток_после = ...
    влияет = отпечаток_после != отпечаток_до
    вернуть старое значение, пересчитать
```

Детали реализации:
- **Положение коробки, а не только размеры.** Размер, который лишь сдвигает
  профиль, тоже управляет геометрией, а объём при этом не меняется.
- **Пересчёт только своего тела** (`o.recompute(True)`). Полный
  `doc.recompute()` заодно пересчитывает сборки с решателем. На mirrored это
  занимало около 25 с на одну пробу, и бюджет кончался после 3 размеров из
  132.
- **Обход по кругу** (`round_robin`): первый размер каждого эскиза, затем
  второй размер каждого… Если время кончится, охват всё равно останется
  равномерным.
- **Размер, привязанный к формуле**, сам не пробуется. Ведущим входом здесь
  служит то, на что ссылается формула.

# Часть 2. `harness.py` — как ставятся оценки

## 2.1. Откуда берётся эталон

`tests/task/reference/baseline.json` хранит замер эталона той же стадией плюс
12 000 точек его поверхности. Внутри записан **хэш `measure_stage.py`**:

```python
if baseline.stage_hash == hash(текущий measure_stage.py):
    взять замороженный замер                  # быстро
else:
    "baseline устарел" → перемерить эталон на лету   # медленно, но верно
```

Это защищает от тихой ошибки, когда стадию поменяли, а эталон остался старым
и кандидата сравнивают с несопоставимыми данными. Пересоздать эталон:
`harness.py --freeze`.

## 2.2. `features()` — из сырого замера в признаки

Перед оценкой замер превращается в удобные признаки. Два нетривиальных шага
описаны ниже.

**Жёсткие группы** (`rigid_groups`). Детали, скреплённые сомкнутыми
`Fixed`-шарнирами, объединяются через union-find: болт + гайка + шайба +
планка = одно жёсткое звено. Это нужно, чтобы понять, соединяет ли подвижный
шарнир действительно разные звенья, или «вращает» деталь, приваренную к
соседней.

**Шаг между осями** (`pivot_spacings`). Для каждого звена берутся оси его
поворотных шарниров и считается расстояние между каждой парой параллельных
осей:

```
d = |(p2 − p1) × a| / |a|     — расстояние между параллельными прямыми
```

Соосные оси (один палец, видимый из двух шарниров) склеиваются в одну.
Получаются **длины звеньев пантографа**; в эталоне это четыре раза по
120 мм. Величина не зависит ни от позы механизма, ни от отражения. Ось
берётся из СК той стороны шарнира, которая принадлежит этому звену, поэтому
несомкнутый шарнир не портит длину звена.

## 2.3. Шесть компонентов

Каждый компонент — число от 0 до 1, кроме ворот. Используются готовые
помощники из `harness_base`:
- `score_error(x, perfect, zero)`: 1.0, пока ошибка не больше `perfect`,
  затем линейно до 0 при `zero`;
- `score_ratio(x, full)`: доля от целевого значения.

Все пороги собраны в словаре `THRESHOLDS` в начале `harness.py`.

### Ворота: `executes and builds geometry` (вес 0, обязательные)

Стадия отработала, и сдано хотя бы одно тело с объёмом больше нуля. Если
ворота не пройдены, весь балл обнуляется.

### 1. `geometry matches ground truth`

**Половина балла — набор деталей** (`inventory_match`). Тела эталона
сопоставляются с телами кандидата жадно, один к одному: самые крупные
первыми, каждому подбирается лучший свободный партнёр.

```
ошибка пары = max относительной ошибки по (объёму, 3 габаритам, 3 моментам)
сходство    = score_error(ошибка, 0.5 %, 5 %)
recall    = Σ объём_эталона × сходство / весь объём эталона     — «чего не хватает»
precision = Σ объём_кандидата × сходство / весь объём кандидата — «что лишнее»
оценка    = F1(recall, precision)
```

Вес по объёму выбран намеренно: два лишних пружинных штифта по 292 мм³ почти
ничего не стоят, а пропавшая планка стоит заметно.

**Половина балла — поза сборки** (`register`). Это совмещение облаков точек:

```
1. центрировать оба облака
2. главные оси (SVD) → 4 стартовые ориентации без отражения
3. из каждого старта ICP, 40 итераций:
      найти ближайшие точки (scipy cKDTree)
      → лучший поворот (алгоритм Кабша с запретом отражения)
4. результат = среднее симметричное расстояние между поверхностями, мм
```

Поворот и сдвиг разрешены: лифт, смоделированный в другой системе координат,
не штрафуется. Оценка: `score_error(расстояние, 4 мм, 25 мм)`. Порог 4 мм
взят от измеренного шума: две разные выборки точек одного эталона расходятся
на 2.3 мм.

**Зеркало.** Совмещение делается дважды: как есть и после отражения облака
кандидата.

```python
if отражённое < 0.85 × прямого:      # отражение подходит явно лучше
    поза = 0.5 × оценка(отражённое)  # это зеркальная сборка: половина балла
```

Здесь я поймал свою ошибку. Сначала стояло
`max(прямое, 0.5 × отражённое)`, но лифт почти симметричен, и у зеркальной
модели прямая подгонка тоже выглядит «хорошо» (4.6 мм, в пределах допуска).
Штраф просто не срабатывал. Решает именно сравнение двух подгонок: 2.8
против 4.6 мм. Для контроля: эталон против другой выборки самого себя даёт
2.3 мм напрямую и 4.4 мм с отражением, то есть отражение у него хуже, как и
должно быть.

### 2. `pantograph joints mated`

```
подвижные = шарниры, кроме Fixed и Grounded
рабочие   = подвижные, которые сомкнуты (gap ≤ 0.05 мм, tilt ≤ 0.5°)
            И соединяют РАЗНЫЕ жёсткие группы

полнота   = min(1, рабочие / рабочие_эталона)   — хватает ли шарниров
точность  = рабочие / все подвижные             — нет ли мусора
оценка    = полнота × точность
```

Пример `dummy_joints`: 12 подвижных шарниров, рабочих 4 (эталон 9).
Получаем 0.44 × 0.33 = 0.15. Множитель «точность» и ловит идею «надуть
счётчик»: лишние шарниры не помогают, а вредят.

### 3. `mechanism articulates`

```
доля   = лучшее чистое перетаскивание: сдвинутые детали / все детали
движ.  = score_ratio(доля, 0.8 × доля эталона)
упор   = для каждого шарнира с пределами: запас хода = min(v − min, max − v)
           запас ≥ 1 мм    → 1.0
           упёрся в предел → 0.5
           вне пределов    → 0.25
оценка = движ. × худший упор
```

Пределы оцениваются по тому, **что они разрешают из текущей позы**. Как
обнаружилось при разведке, `solve()` пределы игнорирует, поэтому
перетаскивание их не проверяет — это делает отдельный множитель «упор». У
`limits_swapped` слайдер стоит ровно на −130, на краю перевёрнутого
диапазона: механизм прижат к упору и может двигаться только в одну сторону.

### 4. `carries dimensional constraints`

```
a = score_ratio(число размеров на СДАННЫХ телах, 0.8 × эталон)
b = score_ratio(доля параметрического объёма,    0.8 × эталон)
оценка = (a + b) / 2
```

Полный балл даётся уже с 80 % от эталона: другой стиль моделирования может
обходиться меньшим числом ограничений, и это не ошибка.

### 5. `dimensions drive the geometry`

```
доля = влияющие / проверенные (только размеры сданных тел)
оценка = score_ratio(доля, 0.9 × доля эталона)
```

Сравнение идёт с долей эталона, а не с 100 %. Даже у эталона 18 % размеров
при изменении на 5 % форму не меняют (в основном это деталь с резьбой).
Требовать от кандидата больше, чем даёт сам эталон, было бы нечестно.

### 6. `signature dimensions present`

Пункты для сверки:
- каждый шаг между осями на звене пантографа (длина звена);
- габариты каждой **крупной** детали эталона (больше 1 % объёма, без
  повторов).

Для каждого пункта ищется ближайший у кандидата, оценка
`score_error(отн. ошибка, 0.5 %, 5 %)`, итог — среднее.

Этот компонент сознательно **не зависит от позы**. Иначе неправильная поза
снималась бы дважды: в геометрии и здесь.

## 2.4. Принцип «не штрафовать дважды»

На этом принципе построена вся раскладка: каждый дефект бьёт ровно в одно
место.

| Дефект | Где наказан | Где сознательно не наказан |
|---|---|---|
| зеркало | поза (половина) | детали, шарниры, механизм |
| несомкнутые шарниры | шарниры | шаг осей: берётся от геометрии каждой стороны |
| неверная поза | поза | характерные размеры: не зависят от позы |
| лишние мелкие детали | precision, по объёму, почти ноль | — |

Конкретный случай, где это сработало. Сначала шаг между осями считался
только по сомкнутым шарнирам, и `dummy_joints` терял 0.25 на характерных
размерах из-за дефекта шарниров. Когда стадия начала записывать систему
координат **каждой** стороны, двойной штраф исчез.

## 2.5. Устойчивость

- Каждый компонент обёрнут в `try`: ошибка в одном даёт 0 с объяснением и не
  роняет остальные.
- Каждое описание говорит, **что измерено**, а не просто «прошёл / не
  прошёл». Например: «4 из 12 подвижных шарниров сомкнуты между разными
  группами (эталон: 9); разошлись: Joint091, Joint042…».
- Ключи запуска:
  - `--freeze` перемеряет эталон;
  - `--score-from ПАПКА [--ref-from ПАПКА]` оценивает готовый замер без
    FreeCAD.

# Часть 3. Результаты

| Модель | Балл | Где теряет |
|---|---|---|
| эталон | **6.00** | — |
| half_finished | 5.67 | геометрия (нет 5 деталей, обрезан верх), характерные размеры |
| mirrored | 5.66 | поза — половина балла; 0.06 — труба ⌀33.7 |
| one_link_missing | 5.27 | геометрия (поза), движение (упирается в предел) |
| limits_swapped | 4.96 | геометрия (поза 0: лифт сложен «наизнанку»), движение (упор) |
| dummy_joints | 4.06 | шарниры 0.15, движение 0 (решатель падает) |

У mirrored, swapped и dummy общие 0.06 на характерных размерах (и ~0.03 на
геометрии) — это труба ⌀33.7: в этих примерах она 58.4 мм, а в эталоне
54 мм. По чертежу L=50 и масса 0.22 кг (~28 000 мм³), и по массе ближе
вариант из примеров. Возможно, ошибка в эталоне; в записке это вынесено
проверяющим.

# Итог в одном абзаце

Стадия открывает документ в FreeCAD, находит сданное изделие (корневую
сборку), измеряет каждое тело величинами, не зависящими от ориентации,
проверяет каждый шарнир (что соединяет, сомкнут ли, где пределы), «шевелит»
механизм эмуляцией перетаскивания и «трогает» каждый размер, проверяя,
меняет ли он форму. Harness сравнивает всё это с таким же замером эталона:
детали — по инвариантам, форму — совмещением облаков точек с отдельной
проверкой зеркала, шарниры — по доле рабочих среди всех, механизм — по
лучшему перетаскиванию и запасу хода до пределов, параметрику — по доле
влияющих размеров относительно эталона. Каждый дефект наказывается в одном
месте, поэтому эталон получает 6 из 6, а каждая сломанная модель теряет баллы
только за то, что в ней действительно сломано.
